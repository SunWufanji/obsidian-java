# IO系统

## 1. 讲一讲 IO 多路复用？

### 先说场景

服务器同时面对很多连接时，最大的问题不是“单个连接读得够不够快”，而是：

**我怎么用尽量少的线程，盯住很多连接，谁有数据我就先处理谁。**

这就是 IO 多路复用想解决的问题。

### 大白话解释

可以把它想成一个服务员盯很多桌客人。

如果一桌配一个服务员，成本很高。

更聪明的办法是：一个服务员同时看很多桌，谁举手了就先去服务谁。

IO 多路复用就是这个思路：

**用一个线程 / 进程，同时监听多个文件描述符，哪个就绪了就处理哪个。**

### 它到底是什么？

IO 多路复用本质上是一种“事件通知机制”。

程序把多个文件描述符交给内核，内核帮它盯着：

- 哪个可读
- 哪个可写
- 哪个出异常

一旦有事件发生，再通知程序来处理。

常见实现就是：

- `select`
- `poll`
- `epoll`

### 为什么它叫“多路复用”？

因为它把“等待多个 IO”的工作，复用到一个或少量线程上完成了。

你不用为每个连接都开一个线程去傻等。

### 它适合什么场景？

典型场景就是高并发网络服务器，比如：

- 聊天服务
- 网关
- Redis / Nginx 这类高并发场景

如果按你图里的说法再往下拆，它的核心味道其实是两点：

- **事件驱动**
- **单线程 / 少线程管理多个 I/O 通道**

也就是说，它不是给每个连接都配一个工人，而是让一个“调度员”专门等事件，谁就绪了就处理谁。

它的优势不是让单个连接更快，而是**让系统用更少资源处理更多连接**。

### 它一般怎么工作？

你可以按这个流程记：

1. 程序把多个文件描述符交给 `select` / `poll` / `epoll`
2. 内核帮你等这些 fd 的状态变化
3. 一旦某些 fd 就绪，就返回通知
4. 程序只处理这些真正就绪的 fd
5. 处理完继续进入下一轮监听

这也是很多事件循环（event loop）的核心思路。

### 实现方式怎么理解？

#### select

- 最早期的多路复用方案
- 有 fd 数量上限
- 每次调用都要重新设置和扫描集合

#### poll

- 和 `select` 思路差不多
- 去掉了固定 fd 数量上限
- 但还是要遍历整个集合

#### epoll

- Linux 下高并发最常见
- 更偏事件通知
- 不需要每次都把所有 fd 无差别全扫一遍

### IO 多路复用的优缺点

#### 优点

- 一个线程能盯很多连接
- 减少线程切换成本
- 高并发场景下资源利用率更高

#### 缺点

- 编程模型更复杂
- `select` / `poll` 在 fd 很多时性能会掉
- 代码往往要围绕事件循环来组织

### ⚠️ 面试易错点

- **IO 多路复用不是“同时真正并行处理多个 IO”**，而是高效地等待和分发多个 IO 事件。
- **它的优势主要是连接数多时系统开销更小**，不是单个请求延迟一定更低。
- **`select`、`poll`、`epoll` 都属于 IO 多路复用机制**。

### 面试回答模板

IO 多路复用是一种 IO 事件监听机制，它允许一个线程或进程同时监听多个文件描述符，把“等待多个 IO 是否就绪”的工作交给内核完成。当某个文件描述符可读或可写时，内核再通知应用程序处理。

它的核心价值在于用更少的线程处理更多连接，减少线程切换和资源开销，典型实现包括 `select`、`poll` 和 `epoll`。

### 面试简答版

IO 多路复用就是一个线程同时监听多个 IO，哪个就绪了就处理哪个，常见实现是 `select`、`poll`、`epoll`。

## 2. Unix 常见的 IO 模型有哪些？

### 先说场景

一次 IO 读数据，通常会经历两件事：

1. 等数据准备好
2. 把数据从内核拷贝到用户空间

不同 IO 模型，本质上就是在解决：

**这两个阶段，进程到底要不要等、怎么等、由谁来通知。**

### 常见五种模型
  
[2021-Java后端工程师必会知识点-(操作系统)面试指南系列，很多情况下不会去深挖细节，是小六六以被面试者的角色去回 - 掘金](https://juejin.cn/post/6942686874301857800#heading-13)
Unix 常见 IO 模型一般有五种：

| 模型 | 核心特点 |
|------|----------|
| 阻塞 IO | 调用后一直等，直到数据准备好并拷贝完成 |
| 非阻塞 IO | 调用后如果没准备好，立刻返回，再反复询问 |
| IO 多路复用 | 先统一等多个描述符就绪，再去读写 |
| 信号驱动 IO | 数据就绪后，内核用信号通知进程 |
| 异步 IO | 连“拷贝到用户空间”都由内核完成，完成后再通知 |

### 怎么理解它们的区别？

最简单的抓法就是看：

- 进程是不是一直自己等
- 内核有没有主动通知
- 数据拷贝这一步是谁负责

### 重点怎么记？

- **阻塞 IO**：最省脑子，但会卡住线程
- **非阻塞 IO**：线程不傻等，但会频繁轮询
- **IO 多路复用**：适合很多连接一起等
- **信号驱动 IO**：靠信号通知
- **异步 IO**：最彻底，内核把准备和拷贝都做完再通知

### 逐个拆开看

#### 1. 阻塞 IO

调用 `read()` / `write()` 之后，如果数据还没准备好，线程就一直等在那里。

优点是简单，缺点是人被拴住了，不能同时干别的活。

更适合：

- 简单程序
- 并发不高
- CPU 不是很忙的场景

#### 2. 非阻塞 IO

如果数据没准备好，系统立刻返回，不让线程一直卡着。

但问题是你得自己一遍一遍问：

“好了没？”

所以它虽然不阻塞，但可能会频繁轮询。

更适合：

- 希望提高响应性
- 可以接受轮询逻辑

#### 3. IO 多路复用

这个前面一题已经展开过了。

核心是：

**一个线程等很多个 fd，哪个就绪了再处理哪个。**

更适合：

- 高并发连接
- 网络服务
- 大量 socket 管理

#### 4. 信号驱动 IO

这种模型是：

先注册信号处理方式，等 I/O 就绪后，内核用信号通知你。

它的好处是不用一直轮询，但程序控制流会更绕，因为信号可能在“半路上”打进来。

更适合：

- 需要及时响应外部事件
- 某些设备驱动或特殊场景

#### 5. 异步 IO

异步 IO 最彻底的地方在于：

**不仅等数据这件事交给内核，连把数据拷到用户空间这一步也交给内核。**

你提交请求后可以先走，等内核整个做完，再通知你“都搞定了”。

这就是它和前面几类最大的区别。

更适合：

- 高性能应用
- 大量并发 I/O
- 不希望线程在 I/O 上浪费时间的场景

### 它和 IO 多路复用是什么关系？

IO 多路复用是五种 IO 模型里的其中一种。

所以你可以把上一题理解成这题的一个子集展开。

### ⚠️ 面试易错点

- **`select` / `poll` / `epoll` 不是五种模型里的三种新模型**，它们都属于 IO 多路复用这一类。
- **同步 / 异步 和 阻塞 / 非阻塞 不是完全同一维度**。
- **异步 IO 的关键不是“快”，而是数据准备和拷贝都由内核完成后再通知应用。**

### 面试回答模板

Unix 常见 IO 模型主要有五种：阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO 和异步 IO。它们的主要区别在于：等待数据的方式不同、内核通知应用的方式不同，以及数据从内核拷贝到用户空间这一步到底由谁来完成。

其中，阻塞 IO 最直接，非阻塞 IO 会不断轮询，IO 多路复用适合同时监听多个连接，信号驱动 IO 通过信号通知，而异步 IO 则由内核把整个 IO 操作做完后再通知应用。

### 面试简答版

Unix 常见 IO 模型有五种：阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO、异步 IO。

它们区别主要在于等待方式和通知方式不同。

## 3. select、poll 和 epoll 之间的区别？

### 先说场景

这三个东西本质上都在做一件事：

**帮你同时监听多个文件描述符，看谁已经就绪。**

所以它们都是 [[05IO系统#1. 讲一讲 IO 多路复用？|IO 多路复用]] 的实现方式。

### 先抓总主线

你不用一上来背很多细节，先记住这三句话：

- `select`：老办法，能用，但限制多
- `poll`：本质和 `select` 很像，只是去掉了一些限制
- `epoll`：更适合高并发场景，Linux 下最常见

### select 是什么特点？

`select` 会把你关心的 fd 集合交给内核，然后内核检查一遍，返回后你自己还得再扫一遍，找出到底哪个 fd 就绪了。

它的问题主要有两个：

- 有最大连接数限制
- 每次都要把 fd 集合从用户态拷到内核态，再整体扫描

连接一多，成本就上来了。

### poll 比 select 强在哪？

`poll` 和 `select` 的核心思路其实差不多，还是：

- 把 fd 列表交给内核
- 内核遍历检查
- 返回后应用再处理

它改进的地方主要是：

- 没有 `select` 那种固定最大 fd 数量限制

但它本质上还是要遍历全部 fd，所以连接很多时，性能问题依然在。

### epoll 为什么更适合高并发？

`epoll` 的核心优势是：

**它不是每次都把所有 fd 重新全量扫描一遍，而是更偏事件驱动。**

你先把关心的 fd 注册给内核，后面哪个 fd 真正就绪了，内核就把它放进就绪队列，你来取就行。

所以在大量连接但只有少量活跃连接的场景里，`epoll` 会非常有优势。

### 再细一点拆：select、poll、epoll 到底差在哪？

如果前面那套说法像“总览版”，这里就是“面试追问版”。

#### select

`select` 用的是 `fd_set` 这种集合。

每次调用时，你都要把想监听的 fd 重新塞进去，再交给内核检查。

它比较吃亏的地方主要是：

- **文件描述符数量有限**，默认常见上限是 `FD_SETSIZE`
- **每次调用都要重新设置集合**
- **每次都要扫描整个集合**

所以它更像“老办法，能用，但连接多了就开始吃力”。

#### poll

`poll` 和 `select` 的思路非常接近，只不过它改成了 `pollfd` 数组来描述事件。

它比 `select` 好一点的地方是：

- 没有 `select` 那种固定得很死的 fd 数量限制
- 传参方式更灵活

但它没有真正摆脱核心问题：

- **每次调用还是要把整组 fd 交给内核**
- **内核还是要一项一项遍历**

所以 `poll` 是“比 `select` 灵活”，但还不是“高并发终极答案”。

#### epoll

`epoll` 更像是把“监听名单”先注册到内核里。

后面你不用每次都把整组 fd 重新交一遍，而是：

- 先注册你关心的 fd
- 再通过 `epoll_wait` 等待就绪事件
- 内核把真正就绪的 fd 通知给你

这就是为什么它在高并发、大量长连接场景下更有优势。

而且 `epoll` 还支持两种触发模式：

- **LT（水平触发）**
- **ET（边缘触发）**

这个我们下一题单独展开。

### 对比总结

| 对比点 | select | poll | epoll |
|--------|--------|------|-------|
| fd 数量限制 | 有 | 没有固定上限 | 没有固定上限 |
| 每次调用是否要全量遍历 | 要 | 要 | 不需要像前两者那样全量扫描 |
| 适合场景 | 连接数少 | 比 select 稍灵活 | 高并发、大量连接 |
| 常见平台 | 通用 | 通用 | Linux |

### 它们各自更适合哪些场景？

这个点你图里给得很细，面试时也很容易被追问。

#### select 适合：

- 连接数不多
- 并发压力不高
- 早期系统或一些兼容性优先的场景

比如：

- 小规模客户端 / 服务端程序
- 简单 demo
- 嵌入式或老系统里的轻量监听

#### poll 适合：

- 比 `select` 稍复杂一点的场景
- fd 数量不固定
- 连接数中等，但还没大到特别夸张

它可以理解成：

**“想比 select 灵活一点，但还没到一定要上 epoll 的程度。”**

#### epoll 适合：

- 高并发
- 大量连接
- I/O 密集型网络服务
- 长连接场景

典型例子：

- Web 服务器
- 聊天服务器
- 网关
- 即时通信
- 实时推流 / 拉流

所以很多 Linux 高性能网络程序，底层都会偏向 `epoll`。

### 为什么大家常说 epoll 是 O(1)？

面试里经常会听到这个说法，但别死背成绝对真理。

更稳妥的说法是：

**在高并发场景下，epoll 不需要像 select / poll 那样每次都无差别扫描全部 fd，所以整体效率通常更高。**

这样回答更稳，也更不容易被追问卡住。

### ⚠️ 面试易错点

- **`poll` 不是本质上完全不同的新机制**，它和 `select` 思路非常接近。
- **`epoll` 的优势主要在高并发、大量连接、少量活跃连接的场景。**
- **不要把 “epoll 一定 O(1)” 背成绝对口号**，面试时说它减少了无差别遍历，更稳。
- **这三者都属于同步 IO**，只是等待事件的机制不同。

### 面试回答模板

`select`、`poll` 和 `epoll` 都是 IO 多路复用的实现方式。`select` 和 `poll` 的核心思路比较接近，都是每次调用时把待监听的 fd 集合交给内核，内核检查后返回结果，因此当连接数很多时，遍历成本较高。

`poll` 相比 `select` 去掉了固定最大 fd 数量的限制，但性能模型本质没有变化。`epoll` 则更适合高并发场景，它采用事件驱动方式，先把 fd 注册到内核中，后续只返回真正就绪的 fd，因此在大量连接场景下效率通常更高。

### 面试简答版

`select`、`poll`、`epoll` 都是 IO 多路复用机制。

`select` 限制多，`poll` 比它灵活一些，但两者都要遍历全部 fd；`epoll` 更适合高并发场景，因为它更偏事件驱动，只关心真正就绪的 fd。

## 4. 读取一个文件的时候，操作系统会发生什么？

### 先说场景

这题特别像面试里的“顺流程题”。

面试官不是只想听你说一句“从磁盘读出来”，而是想听：

**用户态发起请求之后，内核到底做了哪些层层转手。**

### 一条主线先记住

你可以先把它记成这五步：

```text
应用发起 read
-> 进入内核找文件对象
-> 先看页缓存 / 映射
-> 缓存没有再走磁盘 I/O
-> 数据拷回用户空间并更新偏移
```

### 1）应用程序先发起读取请求

通常是应用在用户态调用：

- `read`
- `fread`
- `fgets`

这种函数。

如果是库函数，它们最终也会落到底层系统调用，比如 `read()`。

### 2）进入内核，找到文件相关结构

一旦触发 `read()`，系统会进入内核。

这时操作系统要先确认几件事：

- 这个文件是不是已经打开
- 这个文件描述符是不是合法
- 对应的文件表项是不是有效
- 当前进程有没有权限读

这里通常会涉及：

- **文件描述符**
- **打开文件表**
- **文件控制块 / inode 元数据**

你可以把文件描述符理解成“用户手里的取号单”，内核再通过这个号去找到真正的文件对象。

### 3）先看缓存

这一步特别重要，因为不是每次读文件都真的去敲磁盘。

操作系统通常会先看：

- **页缓存（Page Cache）**
- 或者相关的内存映射区域

如果数据已经在缓存里，就可以直接从内存拿，速度会快很多。

### 4）缓存没有，再走磁盘 I/O

如果缓存里没有，系统才会真正发起磁盘读取。

大致会经过这些环节：

- 根据 inode / 元数据找到文件内容位置
- 文件系统组织读请求
- 块设备层 / 磁盘调度处理请求
- 磁盘控制器把数据读到内存

这一步最慢，因为真正碰到了磁盘。

### 5）把数据交回用户空间

当数据进了内核缓冲区后，如果你用的是普通 `read()`，系统还要把数据：

**从内核空间再拷贝到用户空间缓冲区。**

这时应用程序才真正拿到数据，后续才能继续处理。

### 6）更新文件偏移

每次读完之后，系统通常还会更新文件偏移量。

你可以把它理解成“书签往后挪”。

下次再读，就从新位置继续。

### 7）错误处理

中间如果出问题，也会在这些环节里返回错误，比如：

- 文件不存在
- 权限不足
- 文件描述符无效
- 磁盘 I/O 出错

这时系统会返回错误码，比如 `-1`，并设置 `errno`。

### 如果是 mmap 呢？

如果文件是通过 `mmap` 映射到内存里的，那访问方式会不太一样。

程序更像是在直接访问一段内存，真正缺页时由系统把文件内容按页调进来。

所以 `mmap` 场景下，读取文件这件事会更像“访问映射页”，而不是每次都显式 `read()`。

### ⚠️ 面试易错点

- **读文件不等于每次都访问磁盘**，很多时候先命中页缓存
- **普通 read 通常会有一次“内核 -> 用户”的拷贝**
- **文件描述符不是文件本身**，它只是索引入口
- **mmap 和 read 的读路径不完全一样**

### 面试回答模板

读取文件时，应用程序通常先在用户态调用 `read` 或相关库函数，随后进入内核。操作系统会根据文件描述符找到对应的打开文件表项和 inode 等文件元数据，先检查权限和状态，然后优先查看页缓存中是否已经有目标数据。如果缓存命中，就直接从内存读取；如果没有命中，系统才会发起磁盘 I/O，通过文件系统和块设备层把数据读入内核缓冲区，再从内核空间复制到用户空间缓冲区。读取完成后，系统还会更新文件偏移量，并在出错时返回错误码。

### 面试简答版

读文件时，程序先发起 `read`，内核根据文件描述符找到文件对象，优先查页缓存；缓存没有才走磁盘 I/O。数据读入内核后，再拷到用户空间，并更新文件偏移量。

## 5. 阻塞 IO 和非阻塞 IO 的应用场景问题：一个计算密集型场景，和一个给用户传视频的场景，分别应该用什么 IO？

### 先给结论

- **计算密集型场景**：通常更偏向阻塞 IO
- **视频传输 / 网络高并发场景**：通常更偏向非阻塞 IO 或 IO 多路复用

### 为什么计算密集型场景更偏阻塞 IO？

因为这种场景的瓶颈主要不在 I/O，而在 CPU 计算。

也就是说，程序大部分时间都花在算，而不是花在等数据。

这时如果 I/O 本来就不频繁，使用阻塞 IO 反而更省心：

- 模型简单
- 代码更直
- 不需要为了少量 I/O 引入复杂异步机制

典型例子：

- 数学计算
- 图像处理
- 模型训练中的一部分纯计算流程

### 为什么视频传输场景更偏非阻塞 / 多路复用？

因为视频传输往往是：

- 网络 I/O 多
- 并发连接多
- 单个连接的等待时间不可控

如果一个连接一阻塞就卡住一个线程，那系统很快就顶不住了。

这时候更合适的是：

- 非阻塞 IO
- IO 多路复用（`select/poll/epoll`）

这样一个线程可以同时盯多个连接，谁能发、谁能收，就先处理谁。

### 这题真正想考什么？

其实不是在考“阻塞一定更高级还是非阻塞更高级”，而是在考：

**你的瓶颈到底在 CPU，还是在 I/O 等待。**

如果瓶颈在 CPU，I/O 模型通常不是主战场。  
如果瓶颈在网络等待和并发连接，非阻塞 / 多路复用就会更重要。

### ⚠️ 面试易错点

- **不要机械地说“非阻塞一定比阻塞好”**
- **高并发网络传输场景，更常见的是“非阻塞 + IO 多路复用”**
- **计算密集型程序优化重点往往在 CPU，不在 I/O 模型**

### 面试回答模板

如果是计算密集型场景，程序的主要瓶颈通常在 CPU 计算而不是 I/O，因此往往可以采用阻塞 IO，代码实现更简单，也不会因为 I/O 等待成为主要性能问题。  
如果是给用户传视频这类网络 I/O 密集、并发连接较多的场景，更适合采用非阻塞 IO 或 IO 多路复用，因为这样可以在等待网络数据传输时继续处理其他连接，提高吞吐量和资源利用率。

### 面试简答版

计算密集型场景通常更适合阻塞 IO；视频传输这种高并发网络场景更适合非阻塞 IO 或 IO 多路复用。

## 6. epoll ET 模式和 LT 模式有什么区别？哪一个更高效？

### 先说场景

很多人一听 `epoll`，只记住它“快”。

但面试官往下追的时候，常常会问：

**你知道 `epoll` 还有 LT 和 ET 两种触发模式吗？**

这题本质上是在问：

**内核到底是“反复提醒你”，还是“只提醒你一次”。**

### 先给结论

- **LT（水平触发）**：只要 fd 还处于就绪状态，内核就会继续通知你
- **ET（边缘触发）**：只有状态从“没就绪”变成“就绪”的那一瞬间通知一次

所以你可以把它们想成：

- LT：像老师反复催你，“这题你还没写完”
- ET：像老师只提醒一次，“开始考试了，后面不再喊”

### LT 模式怎么理解？

LT 是默认模式，也更好写。

只要这个 fd 里还有数据没读完，或者还能继续写，`epoll_wait` 下次通常还会继续把它返回给你。

也就是说：

**你这次没处理干净，问题不大，内核还会再提醒你。**

它的特点是：

- 编程简单
- 不容易漏事件
- 更适合普通业务开发

缺点是：

- 通知次数可能更多
- 某些高并发极限场景下不如 ET 激进

### ET 模式怎么理解？

ET 只在“状态发生变化”的边缘提醒一次。

比如一个 socket 原来没数据，现在突然来了数据，内核通知你一次。

如果你这次没有把缓冲区里的数据尽量读空，后面数据状态没再变化，内核可能就**不会再提醒**了。

所以 ET 的关键不是“更神秘”，而是：

**一次通知后，你要自己把活尽量干完。**

它的特点是：

- 通知次数更少
- 更适合高性能、高并发场景
- 但程序写错就容易漏事件

### 为什么大家都说 ET 更高效？

因为它减少了重复通知。

LT 可能会一直告诉你：“这个 fd 还可读。”

ET 则更像说：

“我只提醒你一次，剩下你自己抓紧处理。”

所以从通知次数和系统调用开销上看，ET 通常更激进，也可能更高效。

但这句话后面一定要补半句：

**ET 更高效，不代表业务里一定更合适。**

如果你代码没处理好，比如没有循环读到 `EAGAIN`，反而更容易出 bug。

### 怎么选？

#### 选 LT 的场景

- 普通业务程序
- 先把系统写稳
- 对极限性能没那么苛刻

#### 选 ET 的场景

- 高并发网络服务器
- 非常在意系统调用和重复通知开销
- 团队对非阻塞 I/O 处理足够熟

### ⚠️ 面试易错点

- **LT 不是低级模式，ET 也不是无脑更高级**
- **ET 一般要配合非阻塞 fd 使用**
- **ET 的关键点是：收到通知后要尽量一次性读完 / 写完**
- **如果没有把数据处理干净，ET 场景下可能漏后续事件**

### 面试回答模板

`epoll` 有两种常见触发模式：LT（水平触发）和 ET（边缘触发）。LT 是默认模式，只要文件描述符仍然处于就绪状态，内核就会持续通知应用程序，因此编程更简单，也不容易漏事件。ET 则只在状态从未就绪变为就绪时通知一次，所以通知次数更少，性能通常更高，但要求程序在收到通知后尽量把数据一次性处理完，否则可能漏掉后续事件。

### 面试简答版

LT 是“只要还就绪就一直提醒”，更稳更好写；ET 是“状态变化时只提醒一次”，更高效但更容易写错。一般来说，ET 性能更激进，LT 更适合普通业务开发。

## 7. 零拷贝技术了解过吗？说一下原理

### 先说场景

这题经常出现在网络和文件传输场景里。

比如：

- Web 服务器发静态文件
- 视频服务器传大文件
- 高吞吐网络程序做数据转发

面试官真正想问的是：

**数据在内核态和用户态之间来回搬运了多少次，能不能少搬几次。**

### 什么叫零拷贝？

先别被“零”这个字吓到。

它不一定是字面意义上的“完全一次都不拷”。

更准确地说，它想做的是：

**尽量减少数据在内核空间和用户空间之间的复制，以及减少 CPU 参与搬运的次数。**

### 为什么普通 I/O 会慢？

传统读写里，数据经常要这么跑：

```text
磁盘 -> 内核缓冲区 -> 用户缓冲区 -> socket 缓冲区 -> 网卡
```

你可以把它想成搬家：

本来一箱货能从仓库直接发出去，结果先搬到大厅，再搬到办公室，再搬回装货口。

这中间的来回倒腾，就很浪费 CPU。

### 零拷贝的核心思路

核心就是一句话：

**能不把数据拷到用户态，就尽量别拷；能少一次搬运，就少一次。**

### 常见实现方式

#### 1. `mmap`

`mmap` 会把文件映射到进程的虚拟地址空间。

这样程序访问文件时，更像是在访问一段内存，而不是先 `read` 到用户缓冲区。

它的好处是：

- 少了一次“内核 -> 用户缓冲区”的显式复制
- 适合频繁访问文件内容的场景

但它更适合“访问型”场景，不一定总是最适合“直接往网络发”的场景。

#### 2. `sendfile`

这个是面试里最经典的零拷贝关键词。

它可以把文件内容直接从内核里的文件缓存发到 socket，对应用来说更像一句话：

“这个文件你帮我直接发出去。”

应用程序不需要先把文件读到用户缓冲区，再自己调用 `write` 发出去。

所以它非常适合：

- 静态文件服务器
- 图片 / 视频下载
- 大文件传输

#### 3. Direct I/O

有些资料会把 Direct I/O 和零拷贝一起讲。

它的重点是：

**绕过页缓存，直接和磁盘做数据交换。**

这个思路能减少缓存层带来的额外开销，但它更准确地说是“绕过缓存”，不一定等于我们平常狭义说的零拷贝。

所以面试时最好说得严谨一点：

> Direct I/O 常和零拷贝一起讨论，但它的核心重点是绕过页缓存，不完全等同于 `sendfile` 这类典型零拷贝方案。

### 零拷贝适合哪些场景？

- Web 服务器发静态资源
- 文件下载
- 视频流传输
- 高吞吐转发

尤其是：

**文件 -> 网络** 这种场景，`sendfile` 非常经典。

### 零拷贝的价值是什么？

- 减少数据复制次数
- 减少用户态 / 内核态切换
- 减轻 CPU 负担
- 提高吞吐量

所以它不是“让单个请求变魔法”，而是：

**在大流量、大文件场景下，把系统整体效率拉高。**

### ⚠️ 面试易错点

- **零拷贝不一定真的是“0 次物理复制”**
- **它的重点是减少用户态和内核态之间的复制**
- **`sendfile` 是最常见、最爱被问的零拷贝例子**
- **Direct I/O 更偏绕过页缓存，别和零拷贝完全画等号**

### 面试回答模板

零拷贝是一种减少数据复制次数、提高数据传输效率的技术。传统 I/O 中，数据通常需要在内核空间和用户空间之间来回复制，多次搬运会增加 CPU 开销。零拷贝的核心思想是尽量减少这类复制，让数据尽可能在内核中直接完成传输。常见实现方式有 `mmap` 和 `sendfile`，其中 `sendfile` 特别适合文件直接发送到网络 socket 的场景，比如 Web 服务器发送图片、视频和静态文件。

### 面试简答版

零拷贝就是尽量减少数据在内核态和用户态之间来回复制。典型方式有 `mmap` 和 `sendfile`，其中 `sendfile` 很适合 Web 服务器直接发送静态文件。

## 8. reactor 模式有哪些方案？

### 先说场景

如果说 IO 多路复用是在回答：

**“怎么高效地等很多连接？”**

那 Reactor 模式回答的是：

**“等到事件来了以后，这套程序结构该怎么组织？”**

所以 Reactor 更像一种“并发 I/O 的组织方式”。

### Reactor 模式的大白话理解

你可以把 Reactor 想成一个总调度台。

它不亲自干所有活，而是负责：

- 监听事件
- 发现哪个连接就绪了
- 把任务分发给对应处理器

也就是说：

**Reactor 负责“盯和派”，Handler 负责“干活”。**

### 常见几种 Reactor 方案

#### 1. 单线程单 Reactor

一个线程既负责监听事件，也负责处理事件。

优点：

- 结构简单
- 容易实现
- 没有线程切换和加锁成本

缺点：

- 一旦某个处理步骤慢了，整个系统都会被拖住
- 高并发下容易成为瓶颈

适合：

- 并发不高
- 逻辑简单
- demo / 轻量服务

#### 2. 单线程多 Reactor

这里不是所有事件都交给一个 Reactor，而是拆成多个 Reactor，各自负责一部分事件。

你可以理解成：

- 一个 Reactor 负责连接建立
- 一个 Reactor 负责读写事件

优点：

- 比单 Reactor 更灵活
- 不同类型事件能拆开处理

缺点：

- 结构复杂度开始上升
- 多个 Reactor 的协同需要设计

#### 3. 多线程单 Reactor

一个 Reactor 专门负责监听和分发，后面挂多个工作线程处理业务。

这其实是很多服务端程序很常见的思路：

- 主线程负责等事件
- 工作线程池负责干活

优点：

- 监听和业务处理分离
- 能利用多核
- 并发能力更强

缺点：

- 线程同步和上下文切换成本会上来
- 设计上要处理共享资源问题

#### 4. 多线程多 Reactor

这是更重型的方案。

多个 Reactor + 多个工作线程一起配合：

- 主 Reactor 负责接收连接
- 子 Reactor 负责监听各自连接的读写事件
- 工作线程负责业务处理

优点：

- 扩展性最好
- 最适合高并发、大吞吐
- 更能压榨多核能力

缺点：

- 最复杂
- 线程、事件、连接分配都要设计好
- 对工程实现要求高

### 它和 Proactor 是什么关系？

Reactor 经常和 Proactor 放在一起问。

你可以先抓一句最核心的话：

- **Reactor：事件来了，我自己处理**
- **Proactor：系统做完了，再通知我收结果**

也就是说：

- Reactor 更偏“同步事件就绪通知”
- Proactor 更偏“异步操作完成通知”

### 再拆细一点：Reactor 和 Proactor 的区别

#### Reactor

在 Reactor 模式里，内核通常只负责告诉你：

> “这个 fd 现在可读 / 可写了。”

然后真正的 `read` / `write`，还是应用自己去做。

所以它更像：

**内核告诉你“可以干了”，但活还是你自己干。**

#### Proactor

在 Proactor 模式里，应用先提交一个异步 I/O 请求。

内核或底层 I/O 系统把真正的 I/O 都做完，最后再通知你：

> “事情我做完了，你来拿结果吧。”

所以它更像：

**活系统先干完，再叫你来验收。**

### Reactor 和 Proactor 怎么选？

#### Reactor 更常见于：

- 基于 `select` / `poll` / `epoll` 的网络服务器
- 连接数多、事件驱动明显的场景
- Linux 高性能网络编程

#### Proactor 更常见于：

- 底层异步 I/O 支持较强的系统
- 希望把 I/O 完成过程更多交给系统

### ⚠️ 面试易错点

- **Reactor 不是“异步 I/O 已经做完再通知”**
- **Reactor 更常见是“就绪通知”，不是“完成通知”**
- **Proactor 的门槛通常更依赖底层异步 I/O 能力**
- **很多高性能 Linux 网络程序谈 Reactor，通常默认和 `epoll` 关系很紧**

### 面试回答模板

Reactor 模式是一种事件驱动的并发 I/O 设计模式，它的核心思想是由 Reactor 负责监听 I/O 事件，并在事件就绪后把任务分发给对应的处理器。常见方案包括单线程单 Reactor、单线程多 Reactor、多线程单 Reactor 和多线程多 Reactor。随着并发能力增强，结构也会越来越复杂。

Reactor 和 Proactor 的区别在于：Reactor 更偏向“就绪通知”，内核告诉应用某个 I/O 可以读写了，真正的读写仍由应用完成；而 Proactor 更偏向“完成通知”，应用提交异步 I/O 请求后，由系统完成实际 I/O，完成后再通知应用处理结果。

### 面试简答版

Reactor 是事件驱动模式，负责监听 I/O 事件并分发处理，常见有单线程单 Reactor、多线程单 Reactor、多线程多 Reactor 等方案。它和 Proactor 的核心区别是：Reactor 是“就绪后通知”，Proactor 是“完成后通知”。
