# JVM 调优与故障排查

## 1. JIT 编译器和解释器有什么区别？

解释器像“边翻译边执行”：启动快，但重复执行同一段代码会慢。JIT（即时编译器）会识别热点代码，把字节码编译成本地机器码，之后运行更快。

JVM 会在启动速度、编译成本和长期性能之间动态权衡。JIT 还可做内联、循环优化、逃逸分析、锁消除等优化。

**逃逸分析**判断对象是否逃出方法或线程作用域：若没有逃逸，JIT 可能进行标量替换、栈上分配或锁消除。它是优化机会，不是每个对象都一定栈上分配。

## 2. JVM 常用监控与排障工具有哪些？

- `jps`：找 Java 进程；
- `jcmd`：统一诊断入口，可看 GC、线程、堆信息并导出转储；
- `jstack`：查看线程栈，定位死锁、阻塞、CPU 高线程；
- `jmap` / `jcmd GC.heap_dump`：导出堆转储；
- `jstat`：观察 GC 统计；
- JFR、JMC、VisualVM、MAT：更适合持续分析、火焰图/事件和 heap dump 分析。

**实战顺序：**先用监控确认现象，再抓 JVM 证据，最后修改参数或代码；不要只凭感觉调参数。

## 3. JVM 调优有哪些常见手段？

调优目标先行：是降低 P99 延迟、提高吞吐、减少 Full GC，还是解决 OOM？不同目标的方案不同。

常见动作：

1. 根据容器内存、并发和对象存活情况设置合理堆大小，例如 `-Xms`、`-Xmx`；
2. 结合 JDK 版本和压测选择 GC（常见是 G1；低延迟大堆再评估 ZGC）；
3. 关注元空间、直接内存和线程栈，不只看 Java 堆；
4. 降低无意义对象创建、修复泄漏、限制缓存和队列；
5. 用 GC 日志、JFR、heap dump、线程栈验证修改效果。

⚠️ 不存在放之四海皆准的“最佳 JVM 参数”；脱离业务指标的调参很危险。

## 4. 常见 JVM 故障如何快速定位？

| 现象 | 优先证据 | 常见方向 |
| --- | --- | --- |
| CPU 100% | `top` 找线程 ID，再用 `jstack` 对照 | 死循环、热点计算、频繁自旋、异常重试 |
| Full GC 频繁 / 延迟抖动 | GC 日志、`jstat`、JFR | 堆过小、对象晋升快、泄漏、收集器不匹配 |
| Java 堆 OOM | heap dump、Dominator Tree | 缓存无界、集合累积、大对象、引用未释放 |
| Metaspace OOM | 类加载统计、ClassLoader 引用链 | 动态生成类、热部署类加载器泄漏 |
| `StackOverflowError` | 异常栈 | 无限递归、调用层级过深 |

**面试模板：**“先确认症状和时间窗口，再抓 GC、堆、线程三类证据，依据引用链或线程栈定位根因，最后修代码/参数并压测验证。”
