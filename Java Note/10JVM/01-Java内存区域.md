# Java 内存区域

## 1. JVM 运行时数据区如何划分？每一块做什么？

**先说场景：**线上报 OOM、`StackOverflowError`，或想知道一个对象、局部变量到底放哪儿，先从运行时数据区找答案。

JVM 的运行时内存可先分为两类：**线程私有**和**线程共享**。

- **程序计数器（PC）**：每个线程自己的“执行进度条”，记录当前执行到哪条字节码指令；执行 Native 方法时其值未定义。
- **虚拟机栈**：每次方法调用都会创建一个栈帧，保存局部变量表、操作数栈、动态链接、方法出口；线程私有。
- **本地方法栈**：为 JNI / Native 方法服务；线程私有。
- **堆**：几乎所有对象和数组的主要存放地，线程共享，也是 GC 的主要工作区。
- **方法区（HotSpot 中由元空间实现）**：存放类元数据、运行时常量池、静态变量、JIT 编译后的代码缓存等。

⚠️ **易错点：**“JVM 内存区域”不等于 JMM。前者讲内存**怎么划分**；JMM 讲多线程下的**可见性、原子性和有序性**。

**面试简答：**线程私有的是 PC、虚拟机栈和本地方法栈；线程共享的是堆和方法区/元空间。对象主要在堆，方法执行信息在栈帧，类元数据在元空间。

## 2. 堆和栈有什么区别？

可以把**堆**理解为全公司共用仓库，把每个线程的**栈**理解为该员工手边的临时工作台。

| 对比项 | 堆 | 虚拟机栈 |
| --- | --- | --- |
| 共享性 | 线程共享 | 线程私有 |
| 主要内容 | 对象实例、数组 | 栈帧、局部变量、操作数栈、返回地址 |
| 生命周期 | 通常随对象可达性决定 | 随方法调用入栈、返回出栈 |
| 回收方式 | 主要由 GC 回收 | 栈帧弹出时自然释放 |
| 常见问题 | `OutOfMemoryError: Java heap space` | `StackOverflowError` |

局部变量里的“引用”通常在栈帧中，但它指向的对象通常在堆中；不要把“对象都在栈里”理解成事实。

## 3. 永久代（PermGen）和元空间（Metaspace）有什么区别？

Java 8 前 HotSpot 用永久代保存类元数据；Java 8 起改为**元空间**。

- **PermGen** 位于 JVM 管理的内存中，容量受 `-XX:PermSize`、`-XX:MaxPermSize` 等限制，容易出现 `PermGen space`。
- **Metaspace** 使用本地内存，默认可随系统可用内存增长，但不是无限；可用 `-XX:MaxMetaspaceSize` 设置上限。
- 两者都会涉及类元数据和类卸载；频繁动态生成类（代理、热部署）仍可能发生 `Metaspace` OOM。

**大白话：**从“JVM 给这间资料室固定面积”改成“向操作系统租空间”，弹性更大，但租得太多照样会把机器内存耗尽。

## 4. 方法区和运行时常量池是什么？

方法区是规范中的逻辑概念，HotSpot 中与元空间密切相关，用来存放**类级别信息**：类名、字段、方法、方法字节码、静态变量等。

运行时常量池属于每个类或接口的运行时表示，来自 `.class` 文件的常量池，并可在运行中加入新常量，例如字符串 `intern()` 相关内容。它不是“所有字符串对象都只在这里”。

⚠️ Java 8 后字符串常量池主要在堆中；不要把老版本永久代的说法原样套到新版本。

## 5. 直接内存（Direct Memory）是什么？

直接内存不是 JVM 运行时数据区规范中的一块，却常被 NIO 的 `ByteBuffer.allocateDirect()` 使用。它在堆外的本地内存中，适合与操作系统 I/O 交互，减少一次 Java 堆到内核缓冲区的复制。

优点是大文件或网络 I/O 场景可能更高效；代价是它同样受机器内存约束，常通过 `-XX:MaxDirectMemorySize` 控制。堆没有满也可能报 `OutOfMemoryError: Direct buffer memory`。

## 6. `StackOverflowError` 为什么发生，如何避免？

每个线程的方法调用都会压入一个栈帧。递归没有正确结束、调用层级异常深，或单个栈帧过大时，线程栈空间耗尽，就会抛 `StackOverflowError`。

- 首先检查递归退出条件和循环调用；这通常才是根因。
- 对确有深递归的数据结构，可改成迭代、显式栈或分治。
- `-Xss` 可以调整单个线程栈大小，但调大后可创建的线程数会下降，不能当作首选修复。

## 7. 强、软、弱、虚引用与 `finalize()` 有什么关系？

引用强度从强到弱：

1. **强引用**：普通 `new` 后的引用；只要仍可达，GC 不会回收。
2. **软引用**：内存紧张时才可能被回收，曾用于缓存；现代业务缓存更推荐显式容量和淘汰策略。
3. **弱引用**：下一次 GC 时，只要只剩弱引用，就会回收；`WeakHashMap` 是典型例子。
4. **虚引用**：不能通过它取得对象，只能配合 `ReferenceQueue` 收到对象将被回收的通知，常用于堆外资源清理追踪。

`finalize()` 会使对象进入不可预测的终结流程：执行时间不确定、可能拖慢 GC、还可能发生对象“复活”。它已被废弃，不应用于释放资源；文件、连接等资源用 `try-with-resources` 或显式 `close()`。

## 8. JMM 中的 happens-before 原则是什么？

这题虽然常和 JVM 一起出现，本质上属于并发内存模型。它不是“时间上一定先执行”，而是一条**可见性与有序性保证**：如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，且 A 的执行顺序排在 B 前面。

常见规则：

- 同一线程内，前面的操作 happens-before 后面的操作；
- 对同一把锁，解锁 happens-before 之后的加锁；
- 对 `volatile` 变量，写 happens-before 之后的读；
- `Thread.start()` happens-before 新线程中的动作；
- 线程全部动作 happens-before 另一个线程 `join()` 返回；
- 该关系具有传递性。

**大白话：**happens-before 像一张 JVM 认可的“交接单”。没有它，多线程之间就不能保证一个线程写进去的值，另一个线程马上看得到。详细并发关联见 [[09并发编程/01-并发理论基础]]。
