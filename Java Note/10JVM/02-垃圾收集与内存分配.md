# 垃圾收集与内存分配

## 1. JVM 常见垃圾收集算法有哪些？

GC 的核心目标是：找出无用对象，再尽量低停顿、低碎片地回收内存。

- **标记—清除**：标记垃圾后直接清除；简单，但会产生内存碎片。
- **复制**：把存活对象复制到另一块连续空间；无碎片、分配快，适合存活对象少的年轻代，但需要额外空间。
- **标记—整理**：标记存活对象后向一端移动，再清除边界外空间；避免碎片，移动成本更高，常用于老年代。
- **分代收集**：按对象存活特征分年轻代、老年代，分别采用更合适的策略；这是 HotSpot 常见思路。

⚠️ 算法是思想，收集器是具体实现；例如 G1、ZGC 不是简单等同于某一种算法。

## 2. 常用垃圾收集器有哪些，如何选择？

常见收集器可按目标理解：

- **Serial / Parallel**：吞吐量优先，适合小堆、后台批处理或资源有限场景；Parallel 更强调总吞吐。
- **CMS**：曾追求低停顿，但已废弃；会有碎片和并发模式失败等问题。
- **G1**：把堆划成 Region，可预测停顿目标，适合较大堆的一般服务，是常见默认选择之一。
- **ZGC / Shenandoah**：追求极低停顿，适合大堆、延迟敏感服务；应结合 JDK 版本、运维经验和实际压测选择。

**面试回答重点：**不要背“哪个最好”，要说业务取舍：吞吐、延迟、堆大小、JDK 版本、压测结果。

## 3. JVM 如何判断对象是否死亡？引用计数和可达性分析有什么区别？

JVM 主流采用**可达性分析**：从 GC Roots 出发向下搜索，找不到路径的对象才可能回收。GC Roots 包括线程栈中活跃引用、静态字段、JNI 引用等。

**引用计数法**为对象记录被引用次数，计数归零即可回收，直观但无法处理 A 引用 B、B 引用 A 的循环引用，因此 HotSpot 不以它作为主要判定方式。

不可达也不代表立刻回收：对象可能先经历筛选，带 `finalize()` 的对象还有一次不可靠的终结机会。

## 4. JVM 对象如何分配与回收？

典型流程是：新对象优先在 **Eden** 分配；Eden 不够时触发 Minor/Young GC；存活对象进入 Survivor 区，年龄达到阈值或 Survivor 放不下时晋升老年代；大对象或特定策略下可直接进入老年代。

常见分配优化：

- **TLAB**：每个线程在 Eden 中预分一小块，减少多线程分配竞争；
- **指针碰撞 / 空闲列表**：分别适用于内存规整或不规整的情况；
- **逃逸分析**成功时，部分对象可能栈上分配或被标量替换。

对象不可达后由 GC 回收。实际策略受收集器、堆参数和对象分布影响，不要把“年龄到 15 一定晋升”说成绝对规则。

## 5. Minor GC、Major GC 和 Full GC 分别何时发生？

- **Minor GC / Young GC**：年轻代（通常 Eden）空间不足时发生，频繁但一般较快。
- **Major GC**：常指老年代回收，但不同资料和收集器的术语不完全统一。
- **Full GC**：通常涉及整个堆，可能还涉及元空间，停顿往往更长。

Full GC 常见诱因：老年代不足、对象晋升失败、元空间不足、显式 `System.gc()`（只是建议 JVM 执行）、参数或内存布局不合理等。

⚠️ 面试中先说明“Major GC 定义因收集器而异”，再讲 Full GC 的排查思路，会比死背更严谨。

## 6. 什么是 Safepoint 和 Safe Region？

GC 想准确扫描对象引用时，需要线程停在引用关系稳定的位置。**Safepoint（安全点）**就是 JVM 预先设置的这种检查点；执行长时间循环等代码时线程会在适当位置轮询能否停下。

**Safe Region（安全区域）**是线程处于阻塞、睡眠等状态的一段代码区间；在线程不运行期间，引用关系不会变化，JVM 可以认为它天然安全。

大白话：安全点是“所有人走到指定停车线再检查”，安全区域是“某人已经停在车位里，不会干扰检查”。

## 7. 类卸载是什么？

类不是应用结束才会卸载。在满足条件时，类加载器、该加载器加载的类及其 Class 对象都不再可达，且没有活跃实例等，JVM 才可能卸载这些类并回收元数据。

热部署、插件化、动态代理大量生成类的系统尤其要关注：如果自定义 ClassLoader 被静态集合、线程上下文或缓存长期引用，类无法卸载，就可能造成元空间泄漏。

## 8. 如何诊断和解决内存泄漏？

内存泄漏不是“内存用得高”，而是**本应失效的对象仍被无意引用，无法被 GC 回收**。

排查步骤：

1. 用监控确认堆使用率在 Full GC 后仍持续上升；
2. 用 `jcmd` / `jmap` 导出堆转储，借助 MAT、VisualVM 等查看 Dominator Tree 与引用链；
3. 找到真正的 GC Root，例如静态集合、缓存无上限、未关闭的连接、`ThreadLocal`、监听器或 ClassLoader；
4. 修复引用生命周期，设置缓存上限/过期，及时关闭资源，并回归压测验证。

⚠️ 不要一看到 OOM 就只增大 `-Xmx`；这可能只是把故障推迟。
