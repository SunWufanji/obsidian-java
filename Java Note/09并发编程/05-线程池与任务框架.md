# 线程池与任务框架

> 这一章后续归档：线程池原理、`Executor`、`ThreadPoolExecutor`、`ScheduledThreadPoolExecutor`、`FutureTask`、`Future`、`CompletableFuture`、Fork/Join、`ForkJoinPool` 和异步任务治理。

> ⚠️ 飞书表格把 `ForkJoinPool` 放在并发安全容器附近；但它实际是任务执行框架和线程池，因此本笔记归到本文件。

## 1. 什么是线程池？Java 中如何正确使用线程池？

### 先说场景

Web 服务每来一个请求就新建线程，访问量高时可能创建成千上万个线程，内存和 CPU 都会失控。线程池准备一批可复用的工人，任务来了分配执行，忙不过来就排队或拒绝。

### 核心参数

- `corePoolSize`：常驻核心线程数。
- `maximumPoolSize`：队列满后最多能扩到多少线程。
- `workQueue`：等待任务的队列。
- `keepAliveTime`：非核心线程空闲回收时间。
- `ThreadFactory`：统一命名线程，便于日志排查。
- `RejectedExecutionHandler`：线程与队列都满时的处理策略。

```java
ExecutorService pool = new ThreadPoolExecutor(
    4, 8, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),
    new ThreadPoolExecutor.CallerRunsPolicy());
```

### 执行流程

核心线程未满先创建核心线程 → 核心线程满了先入队 → 队列满了再创建非核心线程 → 达到最大线程数仍放不下，执行拒绝策略。

### 实际使用与易错点

后端通常按业务拆分线程池，例如订单异步处理、文件处理、消息消费各用独立线程池，避免慢任务拖垮所有业务。参数要结合 CPU 核数、任务类型和下游承受能力压测决定。

⚠️ 生产中不建议直接使用 `Executors` 的默认工厂创建无限或过大的队列；应显式使用 `ThreadPoolExecutor`，明确容量、拒绝策略并在停机时 `shutdown()`。

## 2. `Future` 和 `Callable` 有什么作用？

`Runnable` 只能执行任务，`Callable<T>` 可以返回结果并抛出异常；提交 `Callable` 后会得到 `Future<T>`。调用 `future.get()` 可以等待并获取结果，也可以 `cancel()` 尝试取消任务。

`FutureTask` 是 `RunnableFuture` 的常用实现，既能作为任务提交，也能保存最终结果。⚠️ `get()` 会阻塞当前线程，Web 请求线程不能无节制地逐个 `get()`，否则异步又被等回同步。

`FutureTask` 偏向“一个任务对应一个结果”；`CompletableFuture` 更适合多个异步步骤的组合、回调和异常链路。

## 3. 什么是 `Executor` 框架？

`Executor` 把“提交任务”与“如何创建、复用、调度线程”分开。业务只负责提交 `Runnable`/`Callable`，线程池负责线程生命周期、队列和拒绝策略。

常用层次：`Executor` → `ExecutorService`（支持提交、关闭、`Future`）→ `ScheduledExecutorService`（支持延迟和定时任务）。在 Spring Boot 中通常还会配置业务专用的 `ThreadPoolTaskExecutor`。

## 4. Fork/Join 框架是什么？

Fork/Join 适合可拆分的大计算任务：把大任务递归拆成小任务（fork），小任务完成后再合并结果（join）。它使用工作窃取：空闲线程可从其他线程队列尾部“偷”任务，提高 CPU 利用率。

适合数组计算、分治算法等 CPU 密集任务；不适合大量阻塞 I/O。并行流默认也会使用公共 `ForkJoinPool`，后端服务中不要在公共池里随意执行慢阻塞任务。

## 5. `CompletableFuture` 有什么优势？和 `Future` 有什么区别？

`Future` 主要是“提交任务后等结果”；`CompletableFuture` 能把多个异步步骤串联、组合、异常恢复，例如“先查用户，再查订单，最后合并返回”。

常用能力：`thenApply` 转换结果、`thenCompose` 串联异步任务、`thenCombine` 合并两个任务、`exceptionally` 兜底异常。默认异步方法可能用公共线程池，生产中应传入自己的业务线程池，避免和其他任务互相影响。

## 6. 如何避免线程池过度使用导致资源耗尽？

线程池不是越多越好。每个线程都要占栈内存、上下文切换时间和下游资源；线程、队列都无限制时，突发流量可能把内存、数据库连接或第三方接口全部压垮。

做法：按业务隔离线程池；设置有界队列和最大线程数；选择明确拒绝策略；限制提交速率；给任务设置超时；监控活跃线程、队列长度、拒绝次数和耗时。I/O 密集任务与 CPU 密集任务的线程数也要分别评估，不能共用一套拍脑袋参数。

## 7. 可以直接使用 `Executors` 创建线程池吗？

`Executors` 适合学习和简单工具代码，但生产服务更推荐显式构造 `ThreadPoolExecutor`。因为部分工厂方法隐藏了危险默认值：例如无界队列会积压到内存溢出，缓存线程池可能创建过多线程。

显式配置能把线程数、队列容量、线程名、拒绝策略和关闭逻辑写清楚，出了问题也更容易排查。

## 8. Java 线程池如何优雅关闭？

先调用 `shutdown()`：不再接收新任务，但会让已提交任务尽量完成；再用 `awaitTermination()` 等待一段时间；超时后才考虑 `shutdownNow()`，它会尝试中断正在执行的任务并返回尚未执行的任务。

任务本身必须正确响应中断，优雅关闭才真正有效。服务停机时还要停止接流量、处理消息消费确认和资源释放，不能只调用一个 `shutdown()` 就认为万事大吉。
