# 常用锁与同步器

> 这一章后续归档：`Lock`、AQS、`ReentrantLock`、`ReentrantReadWriteLock`、`Condition`、`LockSupport`、`CountDownLatch`、`CyclicBarrier`、`Semaphore` 等。

## 1. `Lock` 接口和 `synchronized` 有什么区别？

### 大白话理解

`synchronized` 是 Java 自带的自动门锁：进入同步块自动加锁，离开自动释放。`Lock`（常用 `ReentrantLock`）是手动使用的高级锁，操作更多，但可做超时、可中断和分组唤醒。

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}
```

| 能力 | `synchronized` | `Lock` / `ReentrantLock` |
| --- | --- | --- |
| 使用方式 | 关键字，自动释放 | API，必须手动释放 |
| 可中断获取锁 | 不直接支持 | `lockInterruptibly()` 支持 |
| 尝试/超时获取 | 不直接支持 | `tryLock()` 支持 |
| 公平锁 | 不可选择 | 可选择公平或非公平 |
| 多条件队列 | `wait/notify` | 多个 `Condition` 可分组唤醒 |

普通、简短的互斥逻辑优先 `synchronized`；需要超时、可中断或多个条件队列时用 `ReentrantLock`。

⚠️ 最大的坑是忘记 `unlock()`，必须放在 `finally` 中。

## 2. `CountDownLatch` 和 `CyclicBarrier` 有什么区别？

两者都用于“等一等”，但等的人和能否复用不同。

| 工具 | 大白话 | 是否可复用 | 常见用途 |
| --- | --- | --- | --- |
| `CountDownLatch` | 主线程等 N 个子任务全部报到 | 否，计数到 0 后不能重置 | 并行加载多个数据后汇总 |
| `CyclicBarrier` | N 个线程彼此等齐后一起进入下一阶段 | 是，可循环使用 | 多线程分阶段计算、回合制任务 |

`CountDownLatch` 中等待者调 `await()`，完成者调 `countDown()`；`CyclicBarrier` 中每个参与者都调 `await()`。前者像老师等所有学生交卷，后者像接力队员全部到位后再出发。

## 3. `Semaphore` 是什么？适合什么场景？

`Semaphore`（信号量）维护一组“许可证”。线程执行 `acquire()` 拿到许可证才能继续，完成后 `release()` 归还。它限制的是**同时访问资源的数量**，而不是像互斥锁那样通常只允许一个线程。

例如第三方接口只允许同时 20 个请求、数据库连接有固定容量、下载任务要限制并发数，都可以用它。⚠️ 必须在 `finally` 中归还许可证，否则许可证泄漏会让后续请求永远等不到。

## 4. `ReadWriteLock` 是什么？为什么能提高读多写少场景的性能？

读写锁把锁分为读锁和写锁：多个读线程可以同时持有读锁；写线程必须独占，写时不能有读或其他写。

它像图书馆：很多人可以同时看书，但有人要修改书内容时，必须等所有读者离开且独自修改。适合缓存配置、字典数据等读远多于写的场景；写很多时额外协调成本未必比普通锁更好。

## 5. `StampedLock` 有什么特点？和读写锁有什么区别？

`StampedLock` 提供读锁、写锁和**乐观读**。乐观读先不真正加读锁，读取后用 stamp 验证期间是否有写入；没写入则直接使用数据，写入过则再退回悲观读锁。

它适合读极多、写很少的场景。⚠️ 它不是可重入锁，也不支持 `Condition`；使用时必须正确释放 stamp，对新手来说比 `ReentrantReadWriteLock` 更容易写错。

## 6. 什么是死锁？如何避免？

死锁是线程 A 拿着锁 1 等锁 2，线程 B 拿着锁 2 等锁 1，双方永远等下去。典型原因是多把锁的获取顺序不一致。

避免方法：统一锁顺序；缩小锁范围；避免锁内再调用外部未知代码；使用 `tryLock` 加超时；必要时通过线程转储定位 `BLOCKED` 线程和锁依赖关系。

大白话：两个人各拿一把钥匙，又都等对方先交钥匙。最可靠的规则是“大家永远先拿 A 再拿 B”。

## 7. 什么是 AQS？它如何工作？

AQS（`AbstractQueuedSynchronizer`）是许多并发工具的基础框架。它用一个 `state` 表示同步状态，用一个 FIFO 等待队列管理没拿到资源的线程。

`ReentrantLock`、`CountDownLatch`、`Semaphore` 等都可基于 AQS 实现不同规则：独占获取、共享获取、可重入计数、许可证数量等。可以把它理解为“排队和发号的通用底座”，具体锁类只需要定义“什么算拿到资源、什么算释放资源”。

## 8. `Phaser` 是什么？和 `CountDownLatch`、`CyclicBarrier` 有何区别？

`Phaser` 是更灵活的分阶段同步器，可以动态注册或注销参与线程，并支持多个 phase。它适合参与者数量会变化的多阶段任务。

`CountDownLatch` 是一次性倒计时；`CyclicBarrier` 是固定数量线程反复集合；`Phaser` 像可随时有人加入或退出的多轮会议。普通业务优先用更简单的工具，确有动态分阶段需求再使用它。

## 9. `LockSupport` 是什么？

`LockSupport` 提供 `park()` 和 `unpark(thread)`：`park` 让线程暂停，`unpark` 给目标线程发一个许可使其继续。它不要求像 `wait/notify` 那样先拿对象监视器，而且“先 unpark、后 park”也不会丢失许可。

它是 AQS 等底层同步器的常用基础工具。业务代码通常优先用锁、条件变量、队列等高层 API，除非确实在实现并发框架。

## 10. `synchronized` 的锁升级是什么？需要手动优化吗？

JVM 会根据竞争情况优化 `synchronized` 的实现：无竞争时尽量使用轻量方式，有竞争时才使用更重的阻塞协调机制。网上常见“偏向锁 → 轻量级锁 → 重量级锁”的说法来自较早版本 JVM；偏向锁已在较新 JDK 中被移除或不再默认使用，因此不能把它当作所有版本的固定流程。

开发者真正该做的是：缩小锁范围、降低共享写入、避免锁内 I/O 和长计算、用线程转储和压测定位竞争，而不是试图手工控制所谓“锁升级”。
