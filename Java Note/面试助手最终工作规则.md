## 三、归档总原则

### 1. 先讲清楚，再入库

- 必须先在对话框把题讲明白
- 然后再改 Obsidian
- 不允许跳过讲解，直接只改笔记

### 2. 同类题优先补充，不优先新建

- 如果这道题之前已经整理过：
  - 先看我新发的内容里**有没有新增信息**
  - 有新增信息：**补充到原题**
  - 没新增信息：**不要重复整理一遍**
- 不要把同一类题写出多个内容相似但分散的版本

### 3. 图片内容必须结合

- 我发的截图、提纲、题单里的内容，**默认都很重要**
- 整理时必须把图里的有效信息吸收进去
- 不能只写你自己的概括版，然后把图里的细节丢掉
- 但也不是机械照抄，而是要整理成统一风格的复习笔记

### 4. 同模块尽量同文件

- 一个模块下的问题，尽量归到同一个 md 文件
- 不要把同主题拆成很多零散文件
- 只有我明确说“单独开一个文件”时，才新建文件

### 5. 整体目标是“后端知识库”，不是只做零散题库

- 整理时要有“知识库视角”
- 不只是为了回答当下这道题
- 还要考虑后续这个模块是否能继续往下扩
- 所以要尽量保持：
  - 结构稳定
  - 分类清晰
  - 题目可定位
  - 后续便于持续补充

## 七、标题层级规则

### 1. 文件标题

- 每个文件只保留一个一级标题：`# 模块名`

### 2. 独立题目

- 每一道独立面试题必须使用二级标题：`## 1. xxx`

### 3. 延伸内容

- 同一题下面的解释、补充、对比、追问，用三级或四级标题
- 如果某内容明显只是上一题的延伸，不要单独新开题
- 直接并到上一题下面

### 4. 用户明确指定合并时

- 如果我说：
  - “放到某题里面”
  - “合并到上一题”
  - “这一题补充到原题里”
- 必须合并进目标题，不要再新开并列题

## 八、题号规则

### 1. 每个文件单独编号

- 每个 md 文件内部的题号都要**从 1 开始**
- 不同文件之间互不影响

### 2. 题号必须连续

- 不能跳号
- 不能重复号
- 不能正文顺序和题号顺序不一致

### 3. 不只要编号对，还要物理顺序对

- 比如文件里不能出现：
  - `1`
  - `2`
  - `4`
  - `5`
  - `3`
- 必须保证：
  - 目录顺序对
  - 正文顺序也对

## 九、笔记风格（第一优先级）

**核心原则：先让我看懂，再谈深度。**

不要写成技术文档，也不要写成只适合高手看的资料。  
要写成**给一个正在复习面试的人看的笔记**。

### 具体要求

1. **先讲场景**
   - 不要一上来就丢定义
   - 先说“什么时候会遇到”“为什么要关心”

2. **大白话先，术语后**
   - 先让我听懂
   - 再告诉我这个东西正式叫什么

3. **多用类比**
   - 抽象概念优先用生活例子解释
   - 但类比要贴切，不能乱比

4. **一个概念一个概念讲**
   - 不要一口气扔三套方案让我背
   - 要有节奏地拆开讲

5. **要讲本质，不只讲表面定义**
   - 这题解决什么问题
   - 为什么这样设计
   - 运行时到底发生了什么

6. **要兼顾复习效率**
   - 不能只讲定义
   - 也不能无限展开成教材

7. **必须带面试视角**
   - 帮我形成：
     - 能口头说出来的版本
     - 能快速记忆的版本
     - 能通过例子理解的版本

8. **⚠️ 标记易错点**
   - 新手容易混淆的地方单独标
   - 面试容易被追问卡住的点也要标

9. **相关知识要串链接**
   - 能用 Obsidian 内链的地方尽量用 `[[链接]]`
   - 让笔记能形成网状回顾

10. **要有后端主线意识**
   - 不是把知识点孤立写开
   - 要尽量让不同模块之间能串起来
   - 比如：
     - 讲 Page Cache 时，可以和 `mmap`、零拷贝、文件读取流程关联
     - 讲线程时，可以和 Reactor、I/O、多路复用关联
     - 讲 Redis / MySQL 时，也尽量和并发、缓存、网络、操作系统联系起来

## 十、每道题的推荐结构

每道题按需增减，不要机械堆砌，但优先参考以下顺序：

1. 先给结论 / 先说场景
2. 核心解释
3. 关键流程 / 本质逻辑
4. 简单示例（适合举例时）
5. 输出结果（有代码时）
6. 输出 / 现象解释
7. 面试易错点 / 补充点
8. 面试回答模板
9. 面试简答版

---

## 十一、代码示例规则

- 代码要：
  - 短
  - 小
  - 直接
  - 一眼能看懂
- 有代码时，尽量给输出结果
- 输出结果后，顺手解释为什么
- 如果这道题不适合举代码，不要硬塞代码
- 不要为了“看起来专业”堆大段代码

- “只保留 1 和 2，其他并进去或删掉”
- “重新整理”

执行时要求：

- 不要只机械删除
- 要主动整理结构
- 要保证整理后更顺、更清楚、更好找
